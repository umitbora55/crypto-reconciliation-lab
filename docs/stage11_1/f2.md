# S11-F2: lossless physical identities in the offline view

The independent 0.9.0 review supplied a valid closed SQLite copy with receipt
IDs 9007199254740992 and 9007199254740993 and matching foreign keys. Its original
export and verifier accepted the numeric SQL capture. Ordinary JavaScript
JSON.parse then rounded both IDs to the same Number, causing each receipt to
join two different effects. This was an incorrect displayed source relationship,
not a financial arithmetic error, invalid signature or operator-pin bypass.

## Narrow repair and presentation contract

Package 0.9.1 retains authoritative run.json, capture.json, report.json, external
expectations, signed material and their hashes/types. Positive SQL IDs remain
supported through 9223372036854775807; the limit is not reduced to the JavaScript
safe integer boundary. Only the derived capture inside data.js changes.

Before the canonical JSON string is encoded, these numeric SQL identity fields
become canonical decimal strings. Null stays null. All fields not listed here,
including hash identifiers, raw SQL TEXT/BLOB representations, amounts and file
identities, retain their existing representation:

| Captured table | Derived string identity columns |
|---|---|
| receipts | id |
| delivery_effects | sequence, core_receipt_id |
| delivery_attempts | id, sequence, effect_sequence |
| auth_configuration | id |
| auth_policy_activations | epoch, previous_epoch |
| auth_keys | first_epoch |
| auth_decisions | id, epoch, sequence |
| auth_delivery_links | sequence, decision_id, core_receipt_id |
| auth_attempt_links | attempt_id, decision_id |

This includes bounded composite-key sequence and policy epoch relationships so
PK/FK joins have one consistent representation. It does not enlarge the valid
sequence/epoch ranges. Bounded input sizes/counts remain numbers. Existing hash
string primary keys require no conversion. Source record JSON and original line
bytes are retained exactly; raw download links continue to serve those files.

The top-level data object still has run, capture, report and materials. Its
double-encoded canonical JSON.parse wrapper and prototype/hostile-text safety
remain intact. The renderer creates a separate projection and does not mutate
the authoritative capture. The independent verifier derives expected strings
from its already typed raw capture rows, without importing the renderer or
trusting exporter-supplied labels, and compares exact data.js bytes. Static
asset byte validation remains mandatory.

The existing strict-equality joins, Sets, details and labels now receive exact
strings before JavaScript parses any identity. The receipt button dataset uses
that existing string directly. Policy-head ordering uses BigInt on the already
exact decimal epoch strings, avoiding lexical ordering such as `10 < 9`; it
does not convert a rounded Number back into an allegedly exact identity.

## Old-view boundary and final evidence

The existing v1 contract binds fixed presentation assets to the installed
reader. The repaired reader rejects an unchanged 0.9.0 view with controlled
PRESENTATION_INTEGRITY / exit 2. This describes incompatible presentation bytes,
not corrupted financial evidence. There is no old faulty-asset allowlist or
in-place upgrade. Re-export a retained closed source DB and exact materials to a
new directory, then independently verify that new manifest. Its digest cannot
reuse an old verification result. Automatic upgrading without the source capture
is outside this repair.

For browser review, the supplied large-ID DB was read unchanged through actual
0.9.1 export/verify CLI commands into f2/browser/witness-large-receipts. Its raw
run/capture/report and signed materials match the independent witness exactly;
external expectations were copied unchanged. Additional small positive,
large-all-ids-rotation, hostile-correction and ambiguous bundles are separate
outputs. The ten real export/verify calls passed their explicit 0/3 expectations.
Final browser observations, source/installed release counts, CI and archive
checks belong to the external final HANDOFF; this focused note does not claim
those checks were performed by the JavaScript harness.
