# S12-F4: recorded process source and request binding

The 0.10.0 release reader hashed each worker request but did not connect its
database or operation to the other workers in the experiment. A policy or
admission contender could name another database while its unchanged BUSY
transcript still passed. This is an evidence-reader defect, not a finding that
the original recorded races used different databases.

The repair is confined to `validate_execution_process_evidence` and three small
release-reader helpers in `scripts/verify_release.py`. No admission runtime,
execution fingerprint, schema, financial calculation or process worker changes
are needed.

## Recorded path policy

The supported producer transcripts use POSIX paths (the existing macOS/Linux
environments). A relative database, snapshot or envelope path is joined to the
worker's **recorded absolute cwd**, then normalized lexically using POSIX
semantics. Absolute paths are normalized the same way. Dot and parent segments
are collapsed. Empty paths, NUL, relative cwd and implementation-defined
double-leading-slash paths are rejected.

The reader never resolves or stats those remote paths. It checks the retained
local evidence members using the existing member guards; that is separate from
interpreting a recorded remote database path. Equivalent relative/absolute
spellings can therefore pass after the evidence is copied to another machine.
Symlink, inode or remote filesystem identity is not inferred.

## Relationships checked

- Every child has its experiment's expected recorded/admission/policy action.
- Interrupted execution and retry target the same database, request identifier,
  normalized UTC cuts and CLI timeout. The requested private barrier matches
  the observed barrier.
- A before-cut writer and its later execution target the same database.
- After-cut holder, contender, successful writer and later execution target the
  same database. The contender and successful writer carry the same admission
  snapshot/envelope paths or policy payload/expected epoch/expected hash.
  The two executions have the same cuts and distinct request identifiers.
- Same-request contention and retry retain one database/request/cut tuple.
- Every successful recorded RESULT has the request identifier and normalized
  cuts in its public request, stored context and financial result.
- Its actual CLI ACK has exactly the expected options, without duplicates; its
  database, request ID, cuts and timeout agree with the worker request.
  The existing exact ACK stdout/result equality check remains.
- Successful policy RESULT epoch and payload agree with the requested prior
  epoch and policy payload. Existing status, PID, barrier, counts, BUSY,
  rollback/commit and scope checks remain.

Binding failures are controlled `ValueError` failures beginning with
`EXECUTION_PROCESS: request binding` or `EXECUTION_PROCESS: ACK binding`.
These checks establish internal transcript consistency. They do not authenticate
a wholly rewritten, self-consistent transcript and do not add a database path
to the runtime request identity.
